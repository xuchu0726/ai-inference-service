Seed-OSS-36B FP32 与 bitsandbytes 量化服务对比总结

一、实验环境

模型：ByteDance-Seed/Seed-OSS-36B-Instruct
服务框架：vLLM 0.11.2
GPU：2 × NVIDIA A100-SXM4-80GB
并行方式：tensor parallel size = 2
上下文配置：max_model_len = 512, max_num_batched_tokens = 512, max_num_seqs = 1
量化路径：vLLM bitsandbytes quantization + load_format=bitsandbytes
测试方式：直接调用 vLLM OpenAI-compatible /v1/chat/completions API，执行 3 次短输出请求，每次 max_tokens=64。

二、FP32 baseline 结果

稳定 serving 显存占用：81147 MiB / GPU
3 次请求平均延迟：3.1106 秒
3 次请求平均 completion tokens/s：20.5746

三、bitsandbytes 量化服务结果

稳定 serving 显存占用：74829 MiB / GPU
3 次请求平均延迟：4.8426 秒
3 次请求平均 completion tokens/s：13.2198

四、量化前后变化

显存下降幅度：7.79%
延迟变化：+55.68%
completion tokens/s 变化：-35.75%

五、阶段性结论

本次实验成功验证了 Seed-OSS-36B-Instruct 在 vLLM 0.11.2 中可以通过 bitsandbytes 量化路径启动并完成 API serving。该路径具备工程可运行性，不再停留在离线脚本或 toy demo 层面。

但是，在当前 2×A100-SXM4-80GB、TP=2、max_model_len=512 的配置下，bitsandbytes 量化没有达到“显存降低 ≥30%、速度提升 ≥20%”的目标。实测结果显示，稳定 serving 显存仅下降约 7.79%，平均延迟反而上升约 55.68%，completion tokens/s 下降约 35.75%。

该结果说明：在线 bitsandbytes 量化并不必然带来端到端 serving 加速。vLLM 场景下的显存占用不仅由模型权重决定，还包括 runtime buffer、KV cache 预分配、通信缓存和执行框架开销。对于大模型推理服务，量化收益需要结合具体量化后端、kernel 支持、tensor parallel 通信、KV cache 策略和请求负载共同判断，不能只从“权重位宽降低”机械推断 serving 性能提升。

六、后续优化方向

当前结果应作为真实工程边界记录，而不是伪造成优化达标结果。下一阶段需要继续探索更适合生产 serving 的优化路径，包括：

1. 对比 BF16 serving profile，建立更接近真实大厂推理服务的生产基线。
2. 继续测试 vLLM 支持的其他量化或压缩路径，判断是否存在更适合 Seed-OSS-36B 的 serving 后端。
3. 从 KV cache、batch profile、max_num_batched_tokens、max_num_seqs 和并发负载角度继续优化，观察吞吐、延迟和显存之间的 trade-off。
4. 在性能优化报告中明确写出：本次 bitsandbytes 量化未达到预期指标，但暴露了量化后端与 serving runtime 之间的真实工程差异。

七、可写入报告的表述

本阶段完成了 Seed-OSS-36B FP32 baseline 与 bitsandbytes 量化 serving 的端到端对比。实验表明，bitsandbytes 量化路径可成功启动并完成 OpenAI-compatible API 推理，但在当前配置下未达到显存降低 ≥30% 和速度提升 ≥20% 的预期目标。该现象反映出大模型推理服务中的量化收益受 runtime 内存预分配、KV cache、kernel 执行效率和 tensor parallel 通信开销共同影响。后续优化将从更适合 serving 的精度配置、量化后端和动态 batch/KV cache 参数调优继续推进。
